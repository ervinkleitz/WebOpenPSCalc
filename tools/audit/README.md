# Payon Stories data audit

Tooling that checks the calculator's numbers against every Payon Stories source:
the wiki, the scraped PS skill DB, the class-rework PDFs, and the live item API.

It lives at the repo root rather than under the backend because the deploy step
rsyncs the whole `open-ps-calc-backend/backend/` directory to the server — nothing
here needs to ship to production.

## Running it

```sh
cd tools/audit
python audit_skills.py                  # every modelled ratio vs every source
python audit_items.py                   # item scripts/descriptions vs the item API
python audit_skills.py GS_TRACKING      # just one skill
```

Both read the committed snapshots and pull *our* side out of the live engine, so
they always compare against current code. Only `refresh`-style runs touch the
network:

```sh
python fetch_ps_mobs.py                 # monster HP/EXP/DEX vs the live tools site
python fetch_wiki.py --diff             # what changed on the wiki since last time
python fetch_wiki.py                    # ...and write the new snapshot
python audit_items.py --refresh         # re-query the item API (~4 min)
python extract_pdfs.py                  # re-extract the PDFs (needs pypdf)
python gen_sources.py                   # rebuild backend/PS_SOURCES.md
```

`fetch_wiki.py --diff` is the one to run first when a patch lands: it names the
pages Payon Stories edited, which is usually a short list and tells you where to
look.

## Layout

| Path | |
|---|---|
| `snapshots/wiki_raw.json` | raw wikitext of every base/2nd-job page, as of the last fetch |
| `snapshots/pdfs.json` | extracted text of the class-rework PDFs |
| `snapshots/api_items.json` | the item API's reply for every hand-authored item |
| `build/` | derived reports — gitignored, cheap to rebuild |

Snapshots are committed on purpose. They are the only copies of things that
cannot be recreated offline (the PDFs live in a personal Downloads folder; the
wiki and API are live and mutable), and committing them makes each audit
**diffable against the last one** rather than a fresh guess.

The human-readable version of the same sources is
[`PS_SOURCES.md`](../../open-ps-calc-backend/backend/PS_SOURCES.md), generated by
`gen_sources.py`.

## Reading the output

Sources disagree constantly, and no single one always wins. The order that has
held up:

1. **A rework PDF beats the wiki and beats `ps_skill_db.json`.** Both lag reworks
   by months. The 2026-08-22 audit found six skills where the wiki still showed
   pre-rework formulas we had already correctly taken from a PDF.
2. **`ps_skill_db.json` is scraped and its `effect` field is not always damage.**
   Proc chance (Triple Attack) and bleed chance (Wounding Shot) have both been
   mistaken for a damage ratio here.
3. **A wiki page can contradict itself.** Tracking's table disagrees with its own
   prose; Shield Boomerang's prose disagrees with its own table. Read both halves
   before believing either.
4. **The item API lags a patch by about a day**, then catches up — and sometimes
   carries terms the PDFs never mentioned. Re-check it a couple of days later.
5. **If nothing resolves a conflict, record it.** Do not pick a side silently.
   Shield Boomerang's Lv1 (130 vs 140) is still open for exactly this reason.

A `DIFF` is a question, not a bug. Two of the 2026-08-22 findings were nearly
filed as bugs off the wiki alone before the PDFs reversed them; both are now
pinned by tests in `test/engine-units.test.js` against repeating that mistake.

## Gotchas

- **Search PDF text with `common.loose_pattern()`, never a plain string.** pypdf
  scatters spaces and ligatures through the output (`Acid T error`, `aﬀected`,
  `Cast Ɵme`). A plain search reported Acid Terror as undocumented when the PDF
  states its formula outright.
- **Cloudflare fronts both the wiki and the item API** and rejects urllib's
  default agent with a 403. Everything goes through `curl` with a real UA.
- **Build Windows paths with `path.join` inside `node -e`.** A `"C:\\..."`
  literal in a shell-quoted script loses its backslashes and silently writes a
  file called `CUserservin...` into the current directory.

`fetch_ps_mobs.py` is the odd one out: there is no monster API, so it resolves the
tools site's current buildId, finds the webpack chunk carrying the monster blob and
parses it. It checks HP, EXP, level, element, race, size and AGI/DEX — and nothing
else, because that is all the site publishes. DEF, MDEF, ATK ranges and skill kits
have no public source; the report ends by saying so, so a clean run is never read as
"the monster database is verified".
